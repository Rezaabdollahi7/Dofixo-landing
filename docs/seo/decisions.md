# تصمیمات معماری — پیشنهادی، نه نهایی

هر رکورد این سند تا وقتی که صراحتاً توسط تیم تأیید نشده،
**پیشنهادی (Proposed)** است، نه **تأیید‌شده (Approved)**. هیچ تصمیمی در
این سند به معنای اجرا یا تغییر کد نیست.

---

## D1 — معماری فرم تماس: Vercel Serverless Function

- **وضعیت:** Proposed
- **گزینه‌های بررسی‌شده:** (A) Vercel Serverless Function روی همین
  ریپو، (B) بک‌اند مجزا روی میزبان دیگر، (C) سرویس بیرونی پردازش فرم
  (Formspree و مشابه).
- **تصمیم پیشنهادی:** گزینهٔ A.
- **استدلال:** این ریپو از قبل روی Vercel با Astro مستقر است؛ افزودن
  یک Function تنها به یک فایل endpoint و یک آداپتور نیاز دارد، بدون
  میزبان/CORS/دیپلوی جدید (گزینه B) و بدون وابستگی به کنترل‌پنل یک
  سرویس بیرونی برای دادهٔ Lead (گزینه C).
- **پیش‌شرط قبل از اجرا:** تأیید نسخهٔ `@astrojs/vercel` سازگار با
  Astro `7.3.5` (`open-investigations.md`).
- **چه کسی باید تأیید کند:** مسئول فنی ریپو.

## D2 — مدل رندر: نگه‌داشتن `output: 'static'` + `prerender = false` روی یک فایل

- **وضعیت:** Proposed
- **گزینه‌های بررسی‌شده:** تنظیم سراسری `output: 'server'` در برابر
  نگه‌داشتن `output: 'static'` (پیش‌فرض فعلی، بدون تغییر) و اضافه‌کردن
  `export const prerender = false` فقط به فایل endpoint جدید.
- **تصمیم پیشنهادی:** گزینهٔ دوم.
- **استدلال:** تقریباً تمام سایت (بیش از ۶۰ صفحه) باید استاتیک بماند؛
  تغییر سراسری به `output: 'server'` یعنی همهٔ صفحات پیش‌فرض
  on-demand می‌شوند مگر صراحتاً `prerender = true` بگیرند — ریسک و حجم
  تغییر بسیار بیشتر از نیاز واقعی (یک endpoint) است.
- **پیش‌شرط:** تأیید این مدل در مستندات رسمی نسخهٔ دقیق Astro نصب‌شده
  هنگام اجرا (این بررسی نتوانست `docs.astro.build` را مستقیماً بخواند —
  `open-investigations.md`).

## D3 — محدودسازی نرخ: فروشگاه کلید-مقدار خارجی به‌جای حافظهٔ داخلی Function

- **وضعیت:** Proposed
- **استدلال:** Function های Vercel بی‌حالت و گذرا هستند؛ شمارندهٔ
  in-memory بین فراخوانی‌های موازی یا بعد از cold start مشترک نیست، پس
  محدودسازی واقعی نرخ درخواست نمی‌دهد. جزئیات کامل در
  `open-investigations.md`.
- **تصمیم پیشنهادی:** استفاده از یک فروشگاه خارجی پایدار (مثال رایج:
  Vercel KV یا یک Redis مدیریت‌شده)؛ نام دقیق سرویس هنوز انتخاب نشده.
- **پیش‌شرط:** انتخاب سرویس توسط تیم (هزینه/عملیات) — **اینجا نامی قفل
  نمی‌شود**.

## D4 — سرویس ارسال ایمیل: هنوز انتخاب نشده

- **وضعیت:** Open (نه حتی Proposed)
- **چرا قفل نشده:** این بررسی نمی‌تواند تأیید کند کدام سرویس بدون نیاز
  به تأیید دامنهٔ فرستنده به یک Gmail تحویل می‌دهد، یا محدودیت پلن
  رایگانش چیست — این نیازمند بررسی مستقیم مستندات هر سرویس در لحظهٔ
  تصمیم‌گیری است، نه فرض از قبل.
- **اقدام بعدی:** تیم فنی باید ۲-۳ گزینه را با معیارهای
  `roadmap.md` (T1.2) مقایسه و اینجا ثبت کند.

## D5 — عدم تغییر رفتار ریدایرکت/Canonical موجود

- **وضعیت:** Approved (ضمنی — این تصمیم به معنای «کاری نکردن» است)
- **استدلال:** تأیید میدانی نشان داد رفتار فعلی canonical و ریدایرکت
  برای about/pricing/features/apex/www سالم است. **هیچ تغییری روی این
  رفتار پیشنهاد نمی‌شود.**

## D6 — عدم ریدایرکت کلیدواژه‌ای بدون بررسی نیت و کیفیت مقصد

- **وضعیت:** Approved (قاعدهٔ کاری، نه یک تغییر کد)
- **استدلال:** طبق قاعدهٔ اولویت‌بندی در `roadmap.md`، هیچ محتوایی صرفاً
  به‌خاطر رقابت ظاهری بر سر یک کلیدواژه ریدایرکت نمی‌شود، مگر نیت
  جستجو و کیفیت صفحهٔ مقصد بررسی شده باشد. نمونهٔ T3.3 (مدیریت تعمیرگاه)
  طبق همین قاعده به پایش موکول شد، نه ریدایرکت فوری.
